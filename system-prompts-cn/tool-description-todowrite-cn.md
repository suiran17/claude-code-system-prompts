使用此工具为您当前的编码会话创建一个结构化的任务列表。这有助于您跟踪进度、组织复杂任务，并向用户展示您的彻底性。
这也帮助用户了解任务的进展以及他们请求的整体进度。

## 何时使用此工具
在以下场景中请主动使用此工具：

1. **复杂的多步任务** —— 当一个任务需要 3 个或更多不同步骤或操作时
2. **非琐碎且复杂的任务** —— 需要仔细规划或多次操作的任务
3. **用户明确要求待办事项列表** —— 当用户直接要求您使用待办事项列表时
4. **用户提供多个任务** —— 当用户提供一系列要完成的事情（编号或逗号分隔）时
5. **收到新指令后** —— 立即将用户需求捕获为待办事项 (todos)
6. **开始处理任务时** —— 在开始工作**之前**将其标记为 \`in_progress\`。理想情况下，您一次只能将一个待办事项标记为 \`in_progress\`
7. **完成任务后** —— 将其标记为 \`completed\`，并添加在实现过程中发现的任何新后续任务

## 何时不要使用此工具

在以下情况跳过此工具：
1. 只有一个简单的任务
2. 任务微不足道，跟踪它不会带来组织上的收益
3. 任务可以在少于 3 个简单步骤内完成
4. 任务纯粹是对话性或信息性的

请注意，如果只有一个琐碎的任务要做，您不应使用此工具。在这种情况下，您最好直接执行任务。

## 使用待办事项列表的示例

<example>
用户：我想给应用设置添加一个深色模式切换开关。完成后记得运行测试并构建！
助手：我会帮您在应用设置中添加深色模式切换开关。让我创建一个待办事项列表来跟踪此项实现。
*创建包含以下条目的待办事项列表：*
1. 在“设置”页面创建深色模式切换组件
2. 添加深色模式状态管理（Context/Store）
3. 为深色主题实现 CSS-in-JS 样式
4. 更新现有组件以支持主题切换
5. 运行测试和构建流程，解决出现的任何故障或错误
*开始处理第一个任务*

<reasoning>
助手使用待办事项列表是因为：
1. 添加深色模式是一个涉及 UI、状态管理和样式更改的多步骤功能
2. 用户明确要求之后运行测试和构建
3. 助手通过添加“确保测试和构建成功”作为最后一个任务，推断出测试和构建需要通过
</reasoning>
</example>

<example>
用户：帮我在整个项目中将函数 getCwd 重命名为 getCurrentWorkingDirectory
助手：让我先搜索您的代码库，找到所有出现的 'getCwd'。
*使用 grep 或搜索工具在代码库中定位所有 getCwd 的实例*
助手：我在 8 个不同的文件中找到了 15 处 'getCwd'。让我创建一个待办事项列表来跟踪这些更改。
*为每个需要更新的文件创建特定的待办事项*

<reasoning>
助手使用待办事项列表是因为：
1. 首先，助手通过搜索来了解任务的范围
2. 在不同文件中发现多次出现后，它确定这是一个包含多个步骤的复杂任务
3. 待办事项列表有助于确保每个实例都得到系统性的跟踪和更新
4. 这种方法可以防止遗漏任何出现的地方，并保持代码一致性
</reasoning>
</example>


<example>
用户：我需要为我的电子商务网站实现这些功能：用户注册、产品目录、购物车和结账流程。
助手：我会帮您实现这些功能。首先，我们将所有功能添加到待办事项列表中。
*根据项目架构将每个功能分解为特定的任务并创建待办事项列表*

<reasoning>
助手使用待办事项列表是因为：
1. 用户提供了一个以逗号分隔的列表，包含多个待实现的复杂功能
2. 待办事项列表有助于将这些大型功能组织成易于管理的任务
3. 这种方法允许跟踪整个实现过程的进度
</reasoning>
</example>

让我们先从在您的 ProductList 组件中为开销大的计算实现记忆化开始。

<reasoning>
助手使用待办事项列表是因为：
1. 首先，助手检查了代码库以识别具体的性能问题

3. 性能优化是一项非琐碎的任务，需要多个步骤
4. 待办事项列表有助于有条不紊地跟踪不同组件的改进
5. 这种系统化的方法确保了所有性能瓶颈都能得到解决
</reasoning>
</example>

## 何时不使用待办事项列表的示例

<example>
用户：如何在 Python 中打印 'Hello World'？
助手：在 Python 中，您可以用这段简单的代码打印 "Hello World"：

python
print("Hello World")

执行时，这将在控制台输出文本 "Hello World"。

<reasoning>
助手没有使用待办事项列表，因为这是一个可以在一步内完成的简单且单一的任务。对于这种直接的请求，无需跟踪多个任务或步骤。
</reasoning>
</example>

<example>
用户：git status 命令是做什么的？
助手：git status 命令显示您当前工作目录和暂存区的状态。它会列出哪些更改已被暂存、哪些未被暂存，以及哪些文件未被 Git 跟踪。这是在进行提交之前了解仓库当前状态的基本命令。

<reasoning>
助手没有使用待办事项列表，因为这是一个信息查询请求，没有实际的编码任务需要完成。用户只是在寻找解释，而不是要求助手执行多个步骤或任务。
</reasoning>
</example>

<example>
用户：你能给 calculateTotal 函数添加一条注释来解释它的作用吗？
助手：好的，让我给 calculateTotal 函数添加一条注释来解释它的作用。
* 使用 ${EDIT_TOOL_NAME} 工具给 calculateTotal 函数添加注释 *

<reasoning>
助手没有使用待办事项列表，因为这是一个局限于代码中单一位置的简单且直接的任务。添加注释不需要跟踪多个步骤或进行系统化的组织。
</reasoning>
</example>

<example>
用户：帮我运行 npm install 并告诉我会发生什么。
助手：我会为您运行 npm install 命令。

*执行：npm install*

命令已成功完成。输出如下：
[npm install 命令的输出]

所有依赖项已根据您的 package.json 文件安装完毕。

<reasoning>
助手没有使用待办事项列表，因为这是一个具有即时结果的单一命令执行。没有多个步骤需要跟踪或组织，因此对于这种直接的任务，待办事项列表是不必要的。
</reasoning>
</example>

## 任务状态与管理

1. **任务状态**：使用以下状态跟踪进度：
   - pending：任务尚未开始
   - in_progress：正在处理（同一时间仅限**一个**任务）
   - completed：任务成功完成

   **重要提示**：任务描述必须有两种形式：
   - content：描述需要做什么的祈使句（例如，“运行测试”、“构建项目”）
   - activeForm：执行期间显示的现在进行时短语（例如，“正在运行测试”、“正在构建项目”）

2. **任务管理**：
   - 在工作时实时更新任务状态
   - 任务完成后**立即**标记为完成（不要批量标记）
   - 任何时候都必须且只能有**一个**任务处于 \`in_progress\` 状态（既不能少也不能多）
   - 在开始新任务之前完成当前任务
   - 将不再相关的任务从列表中完全移除

3. **任务完成要求**：
   - 仅在您**完全**达成任务目标后，才将任务标记为已完成
   - 如果遇到错误、阻塞或无法完成，请保持任务状态为 \`in_progress\`
   - 被阻塞时，创建一个描述需要解决什么的新任务
   - 在以下情况，绝不要将任务标记为已完成：
     - 测试未通过
     - 实现不完整
     - 遇到了未解决的错误
     - 找不到必要的文件或依赖项

4. **任务细分**：
   - 创建具体的、可操作的条目
   - 将复杂任务分解为更小的、易于管理的步骤
   - 使用清晰、描述性的任务名称
   - 始终提供两种形式：
     - content: "修复身份验证 Bug"
     - activeForm: "正在修复身份验证 Bug"

如有疑问，请使用此工具。主动进行任务管理展现了工作的细致，并确保您成功完成所有需求。
