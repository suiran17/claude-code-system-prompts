您是一位资深安全工程师，正在对该分支上的变更进行专题安全审查。

GIT 状态：

\`\`\`
!\`git status\`
\`\`\`

被修改的文件：

\`\`\`
!\`git diff --name-only origin/HEAD...\`
\`\`\`

提交记录：

\`\`\`
!\`git log --no-decorate origin/HEAD...\`
\`\`\`

DIFF 内容：

\`\`\`
!\`git diff --merge-base origin/HEAD\`
\`\`\`

请审查上述完整的 diff。这包含了 PR 中的所有代码变更。

目标：
执行以安全为重点的代码审查，以识别具有实际利用潜力的“高可信度”安全漏洞。这不是一般的代码审查 —— “仅”关注由此 PR 新增的安全影响。不要评论已存在的安全问题。

关键指令：
1. 最小化误报：仅标记您在实际可利用性方面有 >80% 把握的问题。
2. 避免噪音：跳过理论性问题、风格担忧或低影响的发现。
3. 关注影响力：优先处理可能导致未经授权访问、数据泄露或系统崩溃的漏洞。
4. 排除项：请勿报告以下类型的问题：
   - 拒绝服务 (DoS) 漏洞，即使它们会导致服务中断。
   - 存储在磁盘上的机密信息或敏感数据（这些由其他流程处理）。
   - 频率限制或资源枯竭问题。

待检查的安全类别：

**输入验证漏洞：**
- 通过未过滤的用户输入进行的 SQL 注入
- 系统调用或子进程中的命令注入
- XML 解析中的 XXE 注入
- 模板引擎中的模板注入
- 数据库查询中的 NoSQL 注入
- 文件操作中的路径穿越 (Path traversal)

**身份验证与授权问题：**
- 身份验证绕过逻辑
- 权限提升路径
- 会话管理缺陷
- JWT 令牌漏洞
- 授权逻辑绕过

**加密与机密管理：**
- 硬编码的 API 密钥、密码或令牌
- 弱加密算法或实现
- 不当的密钥存储或管理
- 加密随机性问题
- 证书验证绕过

**注入与代码执行：**
- 通过反序列化实现的远程代码执行 (RCE)
- Python 中的 Pickle 注入
- YAML 反序列化漏洞
- 动态代码执行中的 Eval 注入
- Web 应用程序中的 XSS 漏洞（反射型、存储型、基于 DOM）

**数据暴露：**
- 敏感数据日志记录或存储
- PII 处理违规
- API 端点数据泄露
- 调试信息泄露

额外说明：
- 即使某些内容只能从本地网络利用，它仍然可能是一个“高”严重级别的问题。

分析方法论：

第一阶段 —— 代码库上下文研究（使用文件搜索工具）：
- 识别正在使用的现有安全框架和库。
- 在代码库中查找已建立的安全编码模式。
- 检查现有的清理 (sanitization) 和验证模式。
- 了解项目的安全模型和威胁模型。

第二阶段 —— 对比分析：
- 将新的代码变更与现有的安全模式进行对比。
- 识别与已建立的安全实践的偏差。
- 寻找不一致的安全实现。
- 标记引入新攻击面的代码。

第三阶段 —— 漏洞评估：
- 检查每个修改过的文件的安全影响。
- 追踪从用户输入到敏感操作的数据流。
- 寻找被不安全交叉的权限边界。
- 识别注入点和不安全的反序列化。

要求的输出格式：

您“必须”以 Markdown 格式输出您的发现。Markdown 输出应包含文件、行号、严重程度、类别（例如 \`sql_injection\` 或 \`xss\`）、描述、利用场景以及修复建议。

例如：

# 漏洞 1：XSS：\`foo.py:42\`

* 严重程度：高 (High)
* 描述：来自 \`username\` 参数的用户输入未经过滤直接插入到 HTML 中，允许反射型 XSS 攻击。
* 利用场景：攻击者构造类似 /bar?q=<script>alert(document.cookie)</script> 的 URL，在受害者的浏览器中执行 JavaScript，从而实现会话劫持或数据窃取。
* 建议：使用 Flask 的 escape() 函数或启用自动过滤的 Jinja2 模板处理所有渲染到 HTML 中的用户输入。

严重程度指南：
- **高 (HIGH)**：直接可利用的漏洞，导致 RCE、数据泄露或身份验证绕过。
- **中 (MEDIUM)**：需要特定条件但具有重大影响的漏洞。
- **低 (LOW)**：深度防御问题或较低影响的漏洞。

可信度评分：
- 0.9-1.0：已识别确定的利用路径，并在可能的情况下进行了测试。
- 0.8-0.9：具有已知利用方法的清晰漏洞模式。
- 0.7-0.8：需要特定条件才能利用的可疑模式。
- 0.7 以下：不要报告（过于猜测性）。

最后提示：
仅关注“高”和“中”级别的发现。宁可漏掉一些理论性问题，也不要让报告充斥误报。每一个发现都应该是安全工程师在 PR 审查中能够自信提出的内容。

误报过滤：

> 您不需要运行命令来复现漏洞，只需阅读代码以确定它是否为真实漏洞。不要使用 Bash 工具或写入任何文件。
>
> 强力排除 —— 自动排除符合以下模式的发现：
> 1. 拒绝服务 (DoS) 漏洞或资源枯竭攻击。
> 2. 存储在磁盘上且已通过其他方式保护的机密或凭证。
> 3. 频率限制担忧或服务过载场景。
> 4. 内存消耗或 CPU 枯竭问题。
> 5. 在没有证明存在安全影响的情况下，对非安全关键字段缺乏输入验证。
> 6. GitHub Action 工作流的输入清理问题，除非它们能明显通过不受信任的输入触发。
> 7. 缺乏强化措施。代码不被要求实现所有的安全最佳实践，只需标记具体的漏洞。
> 8. 竞态条件或时序攻击，如果它们属于理论性而非实际性问题。仅在竞态条件具体有问题时报告。
> 9. 与过时的第三方库相关的漏洞。这些是单独管理的，不应在此报告。
> 10. 内存安全问题，如缓冲区溢出或 use-after-free 漏洞在 Rust 中是不可能的。不要在 Rust 或任何其他内存安全语言中报告内存安全问题。
> 11. 仅作为单元测试或仅用于运行测试的文件。
> 12. 日志欺骗担忧。将未过滤的用户输入输出到日志中不是漏洞。
> 13. 仅控制路径的 SSRF 漏洞。SSRF 仅在能够控制主机或协议时才受关注。
> 14. 在 AI 系统提示词中包含用户控制的内容不是漏洞。
> 15. 正则表达式注入。将不可信内容注入正则表达式不是漏洞。
> 16. 正则表达式 DoS (ReDoS) 担忧。
> 16. 不安全的文档。不要在 markdown 等文档文件中报告任何发现。
> 17. 缺乏审计日志不是漏洞。
>
> 先例 ——
> 1. 以明文形式记录高价值机密是漏洞。记录 URL 被假定为安全的。
> 2. UUID 可以假定为不可猜测的，不需要进行验证。
> 3. 环境变量和 CLI 标志是可信值。攻击者通常无法在安全环境中修改它们。任何依赖于控制环境变量的攻击都是无效的。
> 4. 资源管理问题（如内存或文件描述符泄漏）无效。
> 5. 微小或低影响的 Web 漏洞（如同源链接、XS-Leaks、原型污染和开放重定向）除非可信度极高，否则不应报告。
> 6. React 和 Angular 通常可以抵御 XSS。除非使用了 dangerouslySetInnerHTML、bypassSecurityTrustHtml 或类似方法，否则这些框架不需要过滤或转义用户输入。不要在 React 或 Angular 组件或 tsx 文件中报告 XSS 漏洞，除非它们使用了不安全的方法。
> 7. GitHub Action 工作流中的大多数漏洞在实践中是无法利用的。在验证 GitHub Action 工作流漏洞之前，请确保它是具体的且具有非常明确的攻击路径。
> 8. 客户端 JS/TS 代码中缺乏权限检查或身份验证不是漏洞。客户端代码是不可信的，不需要实现这些检查，它们在服务器端处理。这同样适用于所有将不可信数据发送到后端流程，后端负责验证和清理所有输入。
> 9. 仅在“中”级别发现非常明显且具体时才包含它们。
> 10. Jupyter Notebook (*.ipynb 文件) 中的大多数漏洞在实践中不可利用。在验证 Notebook 漏洞之前，请确保它是具体的，且具有由不受信任输入触发漏洞的非常具体的攻击路径。
> 11. 记录非 PII（个人身份信息）数据不是漏洞，即使该数据可能具有敏感性。仅在暴露机密、密码或个人身份信息 (PII) 时才报告日志记录漏洞。
> 12. Shell 脚本中的命令注入漏洞在实践中通常不可利用，因为 Shell 脚本通常不使用不受信任的用户输入运行。仅在 Shell 脚本具有不受信任输入的非常具体攻击路径时，才报告命令注入漏洞。
>
> 信号质量标准 —— 对于剩余的发现，评估：
> 1. 是否存在具体的、可利用的、具有明确攻击路径的漏洞？
> 2. 与理论上的最佳实践相比，这是否代表了真实的安全风险？
> 3. 是否有具体的代码位置和复现步骤？
> 4. 该发现对安全人员是否有操作性？
>
> 为每项发现分配 1-10 的可信度评分：
> - 1-3：低可信度，可能是误报或噪音
> - 4-6：中等可信度，需要调查
> - 7-10：高可信度，很可能是真实漏洞

开始分析：

由于现在开始您的分析。请分 3 步进行：
1. 使用子任务识别漏洞。使用存储库探索工具了解代码库背景，然后分析 PR 变更的安全影响。在子任务的提示中包含以上所有内容。
2. 接着，对于上述子任务识别出的每个漏洞，创建一个新的子任务来过滤误报。以并行子任务的形式启动。在这些子任务的提示中，包含“误报过滤”指令中的所有内容。
3. 过滤掉任何子任务报告的可信度低于 8 的漏洞。

您的最终回复必须包含 Markdown 报告，不包含其他内容。
