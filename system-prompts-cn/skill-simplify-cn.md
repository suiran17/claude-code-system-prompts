# 简化：代码审查与清理 (Simplify: Code Review and Cleanup)

审查所有更改的文件，以确保复用性、质量和效率。修复发现的任何问题。

## 第 1 阶段：识别更改

运行 \`git diff\`（如果存在已暂存的更改，则运行 \`git diff HEAD\`）查看更改内容。如果没有 git 更改，请审查用户提到的或您在此对话中早些时候编辑过的最近修改的文件。

## 第 2 阶段：并行启动三个审查智能体

使用 ${AGENT_TOOL_NAME} 工具在单条消息中并发启动所有三个智能体。将完整的 Diff 传递给各智能体，以提供完整的上下文。

### 智能体 1：代码复用审查 (Code Reuse Review)

针对每项更改：

1. **搜索现有的工具函数和助手函数**，以替换新编写的代码。使用 ${GREP_TOOL_NAME} 在代码库的其他地方寻找类似的模式 —— 常见位置包括工具目录、共享模块以及与更改文件相邻的文件。
2. **标记任何重复现有功能的新函数**。建议使用现有的函数代替。
3. **标记任何可以使用现有工具函数的内联逻辑** —— 手写的字符串操作、手动路径处理、自定义环境检查、临时类型守卫以及类似模式通常都是候选对象。

### 智能体 2：代码质量审查 (Code Quality Review)

审查同样的更改是否存在粗糙的模式：

1. **冗余状态**：重复现有状态的状态、可以派生的缓存值、可以是直接调用的观察者 (observers)/副作用 (effects)
2. **参数扩张**：向函数添加新参数，而不是对现有参数进行泛化或结构重组
3. **带有细微变化的复制粘贴**：应通过共享抽象进行统一的近乎重复的代码块
4. **抽象泄漏**：暴露了本应封装的内部细节，或破坏了现有的抽象边界
5. **“以字符串作为类型”的代码 (Stringly-typed code)**：在代码库中已存在常量、枚举（字符串联合类型）或名义类型 (Brand types) 的情况下仍使用原始字符串

### 智能体 3：效率审查 (Efficiency Review)

审查同样的更改是否存在效率问题：

1. **不必要的工作**：冗余计算、重复的文件读取、重复的网络/API 调用、N+1 模式
2. **错失并发机会**：可以在并行运行时却顺序执行的独立操作
3. **热点路径膨胀 (Hot-path bloat)**：在启动过程或每个请求/每个渲染的热点路径中增加了新的阻塞工作
4. **不必要的存在性检查**：在操作前预先检查文件/资源是否存在（TOCTOU 反模式）—— 应直接操作并处理错误
5. **内存问题**：无界的输出结构、缺失清理、事件监听器泄漏
6. **操作过于宽泛**：在只需要一部分时读取整个文件，或在过滤一个项时加载所有项

## 第 3 阶段：修复问题

等待所有三个智能体完成。汇总它们的发现并直接修复每个问题。如果某个发现是误报或不值得处理，请注明并继续 —— 不要与发现结果争论，直接跳过即可。

完成后，简要总结修复了哪些内容（或确认代码已经很整洁）。
