当您即将开始一项非琐碎的实现任务时，请主动使用此工具。在编写代码之前就您的方案获得用户认可，可以避免徒劳的工作并确保方向一致。此工具将让您进入计划模式，在此模式下，您可以探索代码库并设计实现方案供用户审批。

## 何时使用此工具

对于实现任务，除非它们非常简单，否则**优先使用 EnterPlanMode**。当满足以下**任一**条件时，请使用它：

1. **新功能实现**：添加有意义的新功能
   - 示例：“添加注销按钮”——它应该放在哪里？点击时应该发生什么？
   - 示例：“添加表单验证”——有哪些规则？有哪些错误消息？

2. **存在多种可行方案**：任务可以通过几种不同的方式解决
   - 示例：“为 API 添加缓存”——可以使用 Redis、内存、文件等。
   - 示例：“提高性能”——可能有许多优化策略。

3. **代码修改**：影响现有行为或结构的更改
   - 示例：“更新登录流程”——具体应该改变什么？
   - 示例：“重构此组件”——目标架构是什么？

4. **架构决策**：任务需要在模式或技术之间做出选择
   - 示例：“添加实时更新”——WebSocket vs SSE vs 轮询。
   - 示例：“实现状态管理”——Redux vs Context vs 自定义方案。

5. **多文件更改**：任务可能会触及 2-3 个以上的文件
   - 示例：“重构身份验证系统”
   - 示例：“添加一个带测试的新 API 端点”

6. **需求不明确**：在理解完整范围之前需要进行探索
   - 示例：“让应用运行得更快”——需要进行性能分析并识别瓶颈。
   - 示例：“修复结账中的 Bug”——需要调查根本原因。

7. **用户偏好至关重要**：实现方式可能有多种合理的选择
   - 如果您想使用 ${ASK_USER_QUESTION_TOOL_NAME} 来澄清方案，请改用 EnterPlanMode
   - 计划模式允许您先进行探索，然后结合上下文提供选项

## 何时不要使用此工具

仅针对简单任务跳过 EnterPlanMode：
- 单行或几行的修复（拼写错误、明显的 Bug、微调）
- 添加一个需求明确的单一函数
- 用户已给出非常具体、详细指令的任务
- 纯粹的研究/探索任务（请改用带探索智能体的 Agent 工具）

- 显而易见，不需要计划

用户：“添加 console.log 以调试此函数”
- 简单、明显的实现

用户：“哪些文件负责路由？”
- 研究任务，而非实现规划

## 重要提示

- 此工具**需要**用户批准——他们必须同意进入计划模式
- 如果不确定是否使用，请倾向于使用规划——在前期达成一致总比后期返工要好
- 用户喜欢在对其代码库进行重大更改之前被咨询
