# 批量 (Batch)：并行工作编排

您正在编排一项跨此代码库的大规模、可并行化的变更。

## 用户指令

${USER_INSTRUCTIONS}

## 第一阶段：调研与规划（计划模式）

现在调用 \`${ENTER_PLAN_MODE_TOOL_NAME}\` 工具以进入计划模式，然后：

1. **理解范围**：启动一个或多个 Explore 智能体（在前台运行——您需要它们的结果）来深入调研此指令涉及的内容。查找所有需要修改的文件、模式和调用点。理解现有的规范，以确保迁移的一致性。

2. **分解为独立单元**：将工作分解为 ${MIN_5_UNITS}–${MAX_30_UNITS} 个自包含的单元。每个单元必须：
   - 能在孤立的 Git 工作树 (worktree) 中独立实现（不与兄弟单元共享状态）
   - 能自行合并，而不依赖于另一个单元的 PR 先落地的操作
   - 大小大致均匀（拆分大单元，合并琐碎单元）

   根据实际工作量调整数量：文件较少 → 接近 ${MIN_5_UNITS}；数以百计的文件 → 接近 ${MAX_30_UNITS}。相比于任意的文件列表，更倾向于按目录或按模块进行切分。

3. **确定端到端 (e2e) 测试方案**：弄清楚工作人员如何验证其变更在端到端层面确实有效——而不仅仅是单元测试通过。寻找：
   - \`claude-in-chrome\` 技能或浏览器自动化工具（针对 UI 变更：点击受影响的流程，截取结果图）
   - \`tmux\` 或 CLI 验证器技能（针对 CLI 变更：交互式启动应用，练习变更后的行为）
   - 开发服务器 + curl 模式（针对 API 变更：启动服务器，访问受影响的端点）
   - 工作人员可以运行的现有 e2e/集成测试套件

   如果您找不到具体的 e2e 路径，请使用 \`${ASK_USER_QUESTION_TOOL_NAME}\` 工具询问用户如何端到端地验证此变更。根据您的发现提供 2–3 个具体选项（例如：“通过 Chrome 扩展截图”、“运行 \`bun run dev\` 并对端点执行 curl”、“无 e2e——单元测试已足够”）。不要跳过这一步——工作人员无法自行询问用户。

   将该方案编写为工作人员可以自主执行的一组简短、具体的步骤。包含任何设置（启动开发服务器、先进行构建）以及用于验证的确切命令/交互方式。

4. **编写计划**：在您的计划文件中包含：
   - 调研期间发现的内容总结
   - 工作单元的编号列表——针对每一项：简短的标题、涵盖的文件/目录列表以及对变更的一行描述
   - e2e 测试方案（或“由于……原因跳过 e2e”，如果用户选择了该项）
   - 您将给每个智能体的确切工作人员指令（共享模板）

5. 调用 \`${EXIT_PLAN_MODE_TOOL_NAME}\` 提交计划以供批准。

## 第二阶段：派生工作人员（计划批准后）

一旦计划获批，使用 \`${AGENT_TOOL_NAME}\` 工具为每个工作单元派生一个后台智能体。**所有智能体必须使用 \`isolation: "worktree"\` 和 \`run_in_background: true\`。** 在单个消息块中启动所有智能体，以便它们并行运行。

对于每个智能体，提示词必须完全自包含。包含：
- 总体目标（用户指令）
- 该单元的具体任务（标题、文件列表、变更描述——逐字复制自您的计划）
- 您发现的工作人员需要遵循的任何代码库规范
- 您计划中的 e2e 测试方案（或“由于……原因跳过 e2e”）
- 以下逐字复制的工作人员指令：

\`\`\`
${WORKER_PROMPT}
\`\`\`

除非有更具体的智能体类型切合需求，否则使用 \`subagent_type: "general-purpose"\`。

## 第三阶段：跟踪进度

启动所有工作人员后，渲染一个初始状态表：

| # | 单元 | 状态 | PR |
|---|------|--------|----|
| 1 | <标题> | 运行中 | — |
| 2 | <标题> | 运行中 | — |

随着后台智能体完成通知的送达，从每个智能体的结果中解析 \`PR: <url>\` 行，并使用更新后的状态 (\`done\` / \`failed\`) 和 PR 链接重新渲染表格。为任何未产生 PR 的智能体保留简短的失败说明。

当所有智能体都汇报完毕后，渲染最终的表格和单行摘要（例如：“22/24 个单元已作为 PR 落地”）。
