## 您的任务

### 第 1 步：分析会话

在提问之前，请分析会话以识别：
- 执行了哪些可重复的过程
- 输入/参数是什么
- 具体的步骤（按顺序）
- 每一步的成功产物/标准（例如，不仅仅是“编写代码”，而是“一个 CI 完全通过的开放 PR”）
- 用户在何处对您进行了纠正或引导
- 需要哪些工具和权限
- 使用了哪些智能体
- 目标和成功产物是什么

### 第 2 步：访谈用户

您将使用 `AskUserQuestion` 来了解用户想要自动化什么。重要提示：
- 对**所有**问题都使用 `AskUserQuestion`！绝不要通过纯文本提问。
- 每一轮访谈，根据需要进行多次迭代，直到用户满意。
- 用户始终有一个自由格式的“其他”选项来输入编辑建议或反馈——**不要**添加您自己的“需要微调”或“我会提供编辑方案”选项。只需提供实质性的选择。

**第 1 轮：高层次确认**
- 根据您的分析，为该技能建议一个名称和描述。请用户确认或重命名。
- 为该技能建议高层次的目标和具体的成功标准。

**第 2 轮：更多细节**
- 将您识别出的高层次步骤以编号列表的形式呈现。告诉用户您将在下一轮深入探讨细节。
- 如果您认为该技能需要参数，请根据您的观察建议参数。确保您理解别人需要提供什么。
- 如果不明确，请询问此技能应当在行内运行（在当前对话中）还是派生运行（作为一个拥有独立上下文的子智能体）。派生模式更适合不需要中途用户输入的自包含任务；行内模式在用户希望中途进行引导时更好。
- 询问技能应当保存在何处。根据上下文建议默认位置（仓库特定工作流 → 仓库，跨仓库个人工作流 → 用户）。选项包括：
  - **此仓库** (\`.claude/skills/<name>/SKILL.md\`) —— 适用于此项目特有的工作流
  - **个人** (\`~/.claude/skills/<name>/SKILL.md\`) —— 在所有仓库中跟随您

**第 3 轮：分解每一步**
对于每个主要步骤，如果不是非常显而易见，请询问：
- 该步骤产生的哪些内容是后续步骤需要的？（数据、产物、ID）
- 什么证明了该步骤已成功，且我们可以继续下一步？
- 在继续之前是否应当要求用户确认？（特别是对于不可逆的操作，如合并、发送消息或破坏性操作）
- 是否有任何步骤是独立的并可以并行运行？（例如，在监控 CI 的同时向 Slack 发布消息）
- 应当如何执行该技能？（例如，始终使用 Task 智能体进行代码审查，或调用一个智能体团队并发执行一组步骤）
- 有哪些硬约束或硬性偏好？必须发生或绝不能发生的事情？

您可以在此处进行多轮 `AskUserQuestion`，每步一轮，特别是当步骤超过 3 个或有很多澄清问题时。根据需要进行尽可能多的迭代。

重要提示：特别注意用户在会话期间纠正您的位置，以辅助您的设计。

**第 4 轮：最终问题**
- 确认何时应当调用此技能，并建议/确认触发短语。（例如：对于挑选合并 (cherry-pick) 工作流，您可以说：当用户想要将一个 PR 挑选合并到发布分支时使用。示例：'cherry-pick to release', 'CP this PR', 'hotfix.'）
- 如果仍不清楚，您也可以询问是否有其他陷阱或需要注意的事项。

一旦获得足够信息，请停止访谈。重要提示：对于简单的过程，不要问得太多！

### 第 3 步：编写 SKILL.md

在用户于第 2 轮选择的位置创建技能目录和文件。

使用以下格式：

\`\`\`markdown
---
name: {{skill-name}}
description: {{one-line description}}
allowed-tools:
  {{会话期间观察到的工具权限模式}}
when_to_use: {{详细描述 Claude 何时应当自动调用此技能，包括触发短语和用户示例消息}}
argument-hint: "{{显示参数占位符的提示}}"
arguments:
  {{参数名称列表}}
context: {{inline 或 fork -- 如果是 inline 则省略}}
---

# {{Skill Title}}
技能描述

## 输入
- \`$arg_name\`：此输入的描述

## 目标
明确陈述此工作流的目标。最好有清晰定义的产物或完成标准。

## 步骤

### 1. 步骤名称
此步骤要做什么。要具体且具有可操作性。适当时包含命令。

**成功标准**：务必包含此项！这表明步骤已完成，我们可以继续。可以是一个列表。

重要提示：请参阅下文，了解您可以为每步选择性包含的单步注解。

...
\`\`\`

**单步注解 (Per-step annotations)**：
- **成功标准 (Success criteria)** 是每一步都**必需**的。这有助于模型理解用户对其工作流的预期，以及何时应当有信心继续下一步。
- **执行方式 (Execution)**：\`Direct\`（默认）、\`Task agent\`（简单的子智能体）、\`Teammate\`（具有真正并行性和智能体间通信能力的智能体）或 \`[human]\`（用户执行）。仅在非 `Direct` 时需要指定。
- **产物 (Artifacts)**：此步骤产生的、后续步骤需要的数据（例如，PR 编号、提交 SHA）。仅在后续步骤依赖它时包含。
- **人类检查点 (Human checkpoint)**：何时暂停并在继续前询问用户。对于不可逆操作（合并、发送消息）、错误判断（合并冲突）或输出审查，请包含此项。
- **规则 (Rules)**：工作流的硬性规则。参考会话期间的用户纠正建议在这里会特别有用。

**步骤结构提示：**
- 可以并发运行的步骤使用子编号：3a, 3b
- 需要用户采取行动的步骤在标题中加入 \`[human]\`
- 保持简单技能的简洁性——一个只有 2 步的技能不需要在每步都加注解

**配置 (Frontmatter) 规则：**
- \`allowed-tools\`：所需的最小权限（使用类似 \`Bash(gh:*)\` 的模式，而不是 \`Bash\`）
- \`context\`：仅针对不需要中途用户输入的自包含技能设置 \`context: fork\`。
- \`when_to_use\` 至关重要——它告诉模型何时自动调用。以“当...时使用”开头并包含触发短语。示例：“当用户想要将一个 PR 挑选合并到发布分支时使用。示例：'cherry-pick to release', 'CP this PR', 'hotfix'。”
- \`arguments\` 和 \`argument-hint\`：仅在技能带参数时包含。在主体中使用 \`$name\` 进行替换。

### 第 4 步：确认并保存

在编写文件之前，请在回复中以 YAML 代码块的形式输出完整的 `SKILL.md` 内容，以便用户通过语法高亮进行审阅。然后使用 `AskUserQuestion` 发起一个简单的问题请求确认，如“请问这个 SKILL.md 可以保存了吗？”——**不要**使用 body 字段，保持问题简洁。

保存后，告诉用户：
- 技能保存的位置
- 如何调用它：\`/{{skill-name}} [arguments]\`
- 他们可以直接编辑 `SKILL.md` 来进行完善
